# ADR-001: Modular Monolith Architecture

**Status**: Accepted
**Date**: January 2024
**Decision Makers**: Founder / Product Owner

---

## Context

WASL is being built by a single developer. The system needs to serve four user groups (merchants, drivers, admin, customers) with different workflows. The MVP must be built and validated quickly before scaling decisions are made.

Two realistic architecture options were considered:

1. **Microservices**: Independent services for orders, drivers, notifications, payments
2. **Modular monolith**: Single application with clear internal module boundaries

---

## Decision

**Use a modular monolith architecture for the MVP.**

A single Next.js frontend application and a single FastAPI backend application, sharing one PostgreSQL database, deployed as individual units but managed as a coherent whole.

---

## Rationale

| Factor | Microservices | Modular Monolith |
|--------|--------------|-----------------|
| Developer cognitive load | High — multiple codebases, networking, tracing | Low — single codebase |
| Deployment complexity | High — orchestration (Kubernetes or Railway multi-service) | Low — one backend, one frontend |
| Debugging | Hard — distributed tracing required | Simple — single log stream |
| Cost (free tier) | Higher — multiple services | Lower — two services (frontend + backend) |
| Development speed | Slow — API contracts between services | Fast — direct function calls |
| Future scalability | High | Medium (extract services later if needed) |
| Solo developer suitability | Poor | Excellent |

The modular monolith achieves the same logical separation (auth, orders, drivers, admin) through **code organisation** (folders, modules, services) rather than network boundaries. This is maintainable at MVP scale and can be decomposed later if needed.

---

## Consequences

**Positive:**
- Single deployment unit is simpler to operate and debug
- No inter-service network latency
- All business logic in one place — easier to understand and change
- Shared database transaction support (ACID across service boundaries)
- Lower infrastructure cost during MVP

**Negative / Trade-offs:**
- Scaling is vertical (larger server) before service extraction
- All modules share the same deployment cycle
- Database schema shared across all logical domains (requires discipline)
- Team expansion later will require refactoring to avoid stepping on each other

---

## Mitigations

- Enforce module boundaries through folder structure: `/routers`, `/services`, `/models` per domain
- Services communicate via function calls, not direct database queries across domains
- Avoid importing from one domain's service into another's router
- Document service interfaces as if they were APIs — makes future extraction easier

---

## Future Review

Revisit this decision if:
- Team grows beyond 3 developers and merge conflicts become frequent
- Database becomes a bottleneck (high write load on a single table)
- Deployment frequency is constrained by monolith build times
- A single service needs dramatically different scaling than others

**Earliest review point**: Month 6 post-launch, after initial scaling data is available.

---

## Alternatives Considered

### Microservices
Rejected for MVP. Too complex for one developer. Network overhead, distributed tracing, and inter-service authentication add months of infrastructure work before any user-facing feature is delivered.

### Serverless (FaaS)
Rejected. Cold starts introduce unpredictable latency for driver task updates. State management across serverless functions is complex. Vendor lock-in risk.
