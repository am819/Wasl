# ADR-002: PostgreSQL as Single Data Store (No Cache or Queue in MVP)

**Status**: Accepted
**Date**: January 2024
**Decision Makers**: Founder / Product Owner

---

## Context

The WASL MVP requires:
- Persistent storage for orders, users, financial records
- Some near-real-time behaviour (driver task notification, order status updates)
- Background processing (weekly settlement calculation, stats recalculation)

Options considered for the data layer:
1. **PostgreSQL only** — polling for updates, synchronous processing
2. **PostgreSQL + Redis** — caching, pub/sub for real-time, session storage
3. **PostgreSQL + Redis + Celery** — full async background job processing

---

## Decision

**Use PostgreSQL as the only data store in the MVP. No Redis, no Celery, no message queues.**

Real-time updates are handled by client-side polling. Background tasks (settlements, stats) are triggered manually by admin or run synchronously at request time.

---

## Rationale

### Why No Redis (MVP)

The most common reasons to add Redis are:
- **Session storage**: JWT tokens handle authentication statelessly — Redis not needed
- **Caching**: MVP query load is low; database queries will be fast enough without caching
- **Real-time pub/sub**: Driver notifications can use polling (5–10 second intervals) at MVP scale

Adding Redis requires:
- Additional managed service (Railway or Upstash)
- Connection management in FastAPI
- Cache invalidation logic
- Additional operational monitoring

This overhead is not justified at MVP scale.

### Why No Celery (MVP)

Celery is used for background job processing. In MVP:
- Settlement processing is **admin-triggered** (not scheduled)
- Stats recalculation can run synchronously (daily admin action or on-demand)
- Email sending is low volume and acceptable synchronously

Celery requires a message broker (Redis or RabbitMQ), worker process management, task monitoring, and retry logic. Too complex for MVP.

### PostgreSQL Is Sufficient

PostgreSQL can handle:
- All CRUD operations
- Complex queries for analytics and reporting
- JSONB for flexible fields
- Concurrent connections (with PgBouncer if needed)
- ACID transactions for financial records

At MVP scale (< 1,000 orders/day), a single PostgreSQL instance on Railway or Supabase free tier is more than sufficient.

---

## Consequences

**Positive:**
- Simpler infrastructure — one database, one connection string
- Lower operational cost (one managed service vs. three)
- Easier debugging — no distributed state
- Fewer failure modes

**Negative / Trade-offs:**
- Driver task notifications have 5–10 second latency (polling interval)
- Settlement processing is manual (admin triggers weekly)
- Stats recalculation is synchronous (slight dashboard delay acceptable)
- No retry mechanism for failed operations (must be handled in application code)

---

## Polling Approach for Driver Notifications

The driver portal polls `GET /api/v1/drivers/tasks` every 10 seconds.

```
Driver browser → polling every 10s → FastAPI → PostgreSQL query
```

At MVP scale (100 concurrent drivers):
- 100 drivers × 6 requests/minute = 600 requests/minute
- Each request is a lightweight indexed query
- Well within PostgreSQL and FastAPI capacity

This is acceptable. Latency of up to 10 seconds between admin assignment and driver notification is operationally fine for the MVP.

---

## Migration Path

If real-time requirements become critical post-MVP:

1. **Add Upstash Redis** (managed, free tier) for session storage and pub/sub
2. **Switch driver notifications to WebSocket** with Redis pub/sub backend
3. **Add Celery + Redis** for background jobs (settlements, stats recalc, emails)

This migration does not require changing the PostgreSQL schema or the business logic — only adding a new transport layer.

---

## Future Review

Revisit this decision if:
- Driver notification latency > 30 seconds becomes an operational complaint
- Email sending blocks API responses for > 2 seconds
- Database connection pool is saturated under normal load
- New features require true real-time event streaming

**Earliest review point**: Month 4, once load patterns from real operation are known.

---

## Alternatives Considered

### PostgreSQL + Redis
Rejected for MVP. Additional complexity without clear benefit at current scale. Can be added post-MVP.

### PostgreSQL + Redis + Celery
Rejected for MVP. Full async infrastructure requires significant setup and operational overhead. Deferred to Phase 2 or 3.

### Supabase Realtime
Considered. Supabase provides a WebSocket layer over PostgreSQL for free. May revisit as an alternative to polling without adding Redis manually.
