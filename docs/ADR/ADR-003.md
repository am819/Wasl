# ADR-003: JWT Authentication with HS256 (Symmetric Key)

**Status**: Accepted with documented migration path
**Date**: January 2024
**Decision Makers**: Founder / Product Owner

---

## Context

WASL needs a stateless authentication mechanism that:
- Works across the Next.js frontend and FastAPI backend
- Supports role-based access control (merchant, driver, admin)
- Does not require a shared session store (no Redis in MVP)
- Is straightforward to implement and debug for a solo developer

Options considered:
1. **JWT with HS256** — symmetric HMAC key shared between issuer and validator
2. **JWT with RS256** — asymmetric RSA keypair (private key signs, public key verifies)
3. **Session-based authentication** — server-side session storage
4. **OAuth 2.0** — delegated authorisation framework

---

## Decision

**Use JWT tokens signed with HS256 (HMAC-SHA256) for the MVP.**

Access tokens expire in 24 hours. Refresh tokens expire in 7 days, are stored in the database, and are single-use.

---

## Token Specification

### Access Token

| Property | Value |
|----------|-------|
| Algorithm | HS256 |
| Expiry | 24 hours |
| Payload | `user_id`, `email`, `role`, `merchant_id` or `driver_id`, `iat`, `exp` |
| Signing key | `JWT_SECRET_KEY` environment variable (32+ byte random string) |

### Refresh Token

| Property | Value |
|----------|-------|
| Storage | `user_sessions` database table |
| Expiry | 7 days |
| Usage | Single-use (invalidated on use) |
| Revocation | Deleted on logout; new login invalidates all previous |

---

## Rationale

### Why HS256 over RS256 (for MVP)

**HS256 (symmetric)**:
- Single secret key used for both signing and verification
- Simpler key management — one environment variable
- Faster token generation and validation
- No PKI infrastructure required
- Sufficient for a monolith where frontend and backend are the same trust domain

**RS256 (asymmetric)**:
- Private key signs tokens; public key verifies
- Required when tokens need to be verified by third parties
- Necessary for true service-to-service authentication
- Adds key management complexity (key rotation, public key distribution)

In the MVP monolith, the frontend and backend are operated by the same entity. There are no third-party services validating tokens. HS256 is appropriate.

### Why Not Session-Based Authentication

Session-based auth requires server-side state (session store). This conflicts with the decision not to introduce Redis (ADR-002). Stateless JWTs work without a session store.

### Why Not OAuth 2.0

OAuth 2.0 is an authorisation delegation framework — appropriate when users grant third-party apps access to their data. WASL's MVP has no third-party integrations. OAuth 2.0 adds significant complexity (authorisation server, token introspection endpoints, scopes) without benefit at this stage.

## Security Considerations

### Key Strength

`JWT_SECRET_KEY` must be:
- Minimum 32 bytes (256 bits) of cryptographically random data
- Generated with `secrets.token_urlsafe(32)` or `openssl rand -base64 32`
- Never committed to version control
- Rotated every 90 days in production

### Token Revocation

JWT tokens are stateless — they cannot be individually revoked before expiry.

Mitigations:
- **Short access token lifetime** (24 hours): Limits window of abuse
- **Refresh token in database**: Logout invalidates refresh token, preventing renewal
- **New login invalidates all previous refresh tokens**: Limits concurrent session abuse
- **Key rotation**: Rotating `JWT_SECRET_KEY` invalidates all active tokens (use for security incidents)

### HS256 Limitation

The signing key is known to the backend only. If the backend is compromised, an attacker could forge tokens. This is an inherent limitation of symmetric keys.

Mitigation: Harden backend infrastructure (no public SSH access, environment variables in platform dashboard, not in code).

---

## Consequences

**Positive:**
- Simple to implement — PyJWT library, one environment variable
- No external dependencies for token validation
- Fast — HMAC is computationally inexpensive
- Easy to debug — decode token with JWT debugger for inspection

**Negative / Trade-offs:**
- Cannot issue tokens for third-party service consumption
- Key rotation invalidates all active sessions simultaneously
- No cryptographic proof of token origin for external parties
- Not suitable if WASL later exposes a public API for merchant integrations

---

## Migration Path to RS256

When WASL introduces third-party integrations or true microservices:

1. Generate RSA keypair on the server:
   ```bash
   openssl genrsa -out private.pem 2048
   openssl rsa -in private.pem -pubout -out public.pem
   ```
2. Update FastAPI to sign tokens with `private.pem`
3. Publish `public.pem` at a `.well-known/jwks.json` endpoint
4. Any service can now verify tokens without the private key
5. Update `SECURITY.md` with new key rotation procedure

**This migration does not require changes to the database schema or business logic** — only the JWT signing/verification code.

## Future Review

Revisit this decision if:
- WASL introduces a public merchant API (third parties need to verify tokens)
- Microservices are extracted and need service-to-service auth
- A security audit recommends asymmetric keys

**Earliest review point**: Month 6, when merchant API integration is planned.

---

## Alternatives Considered

### RS256
Rejected for MVP. Adds key management complexity without benefit in a single-service deployment.

### Paseto (Platform-Agnostic Security Tokens)
Considered but less widely supported. Stick with JWT for ecosystem compatibility.

### Session Cookies (server-side)
Rejected. Requires session store (Redis) which is deferred. Stateless JWT is cleaner.
