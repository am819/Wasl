# ADR-006: Web-Only MVP (No Native Mobile Applications)

**Status**: Accepted
**Date**: January 2024
**Decision Makers**: Founder / Product Owner

---

## Context

WASL's three user portals (merchant, driver, admin) could be delivered as:

1. **Native mobile apps** (iOS + Android) for merchants and drivers
2. **Responsive web application** accessible from any browser on any device
3. **Hybrid** — web for merchants and admin, native app for drivers

Drivers in particular are likely to access WASL primarily on mobile devices. The question is whether a mobile browser experience is sufficient, or whether a native app is necessary for the MVP.

---

## Decision

**Build a responsive web application only for the MVP. No native iOS or Android applications.**

All three portals (merchant, driver, admin) will be responsive web pages built with Next.js and Tailwind CSS, optimised for both desktop and mobile browsers.

---

## Rationale

### Why Web-Only

**Single codebase**: One Next.js application serves all devices. A solo developer cannot realistically maintain three separate codebases (web, iOS, Android) while building features.

**Faster delivery**: Native app development adds approximately 8–12 weeks for React Native setup, platform-specific testing, App Store / Play Store submission, and review cycles. The web MVP can launch in 12 weeks.

**No app store dependency**: Web apps deploy instantly. Native apps require App Store review (Apple: 1–3 days), Play Store review (Google: 1–7 days), and user app updates. A web deployment takes minutes.

**Cost**: Apple Developer Programme costs $99/year. No equivalent cost for web.

**Sufficient capability**: Modern mobile browsers support:
- Touch-optimised interfaces
- Camera access (for delivery photos — future)
- Location awareness (for future GPS features)
- Installable as PWA (Progressive Web App) with home screen icon

**Validation first**: The business model has not been validated. Building native apps before proving product-market fit risks significant wasted investment.

### Why Not Native Apps (MVP)

| Concern | Web Approach | Native App |
|---------|-------------|-----------|
| Reach | Any device with browser | Requires install |
| Distribution | Instant URL share | App store download |
| Updates | Instant | App store update cycle |
| Development time | Included in 12-week plan | +8–12 weeks |
| Maintenance | One codebase | Three codebases |
| Push notifications | Browser notifications (limited) | Native push |
| Offline support | Limited (with PWA) | Full offline capable |

The push notification limitation is the most significant gap. Drivers cannot receive OS-level push notifications in a web app. This is acceptable in MVP because:
- Drivers are expected to keep their browser open while on duty
- Polling every 10 seconds provides adequate notification latency for the MVP
- Admin assigns tasks; drivers check their task queue actively

### Why Not React Native

React Native would share some business logic with the web frontend, but still requires:
- Separate navigation structure
- Platform-specific UI components
- Native build toolchain (Xcode for iOS, Android Studio for Android)
- App store management

The code sharing benefits do not outweigh the complexity at MVP scale.

---

## Progressive Web App (PWA) Enhancement

To improve the mobile experience without a native app, the web application will be made installable as a PWA:

- **Add to home screen**: Users can install the web app as an icon on their phone
- **Service worker**: Enables basic caching for faster repeat loads
- **App-like feel**: Full-screen mode, custom splash screen
- **Offline indicator**: Warn users when connectivity is lost

This provides most of the UX benefits of a native app without the development overhead.

---

## Consequences

**Positive:**
- 12-week MVP timeline achievable for solo developer
- Single codebase to maintain and debug
- No app store submission delays
- Instant deployment of updates
- Works on all devices without installation

**Negative / Trade-offs:**
- No OS-level push notifications (drivers must keep browser open)
- Less "native" feel (no platform-specific animations or haptics)
- No offline mode without significant PWA investment
- Background location tracking not possible (required for future GPS features)
- Some users may expect a "proper app" and perceive web as less professional

---

## User Experience Approach

To minimise the disadvantages:

1. **Mobile-first design**: All interfaces designed for small screens first
2. **Large touch targets**: Buttons and actions sized for fingers, not cursors
3. **PWA installation prompt**: Prompt drivers to install to home screen on first login
4. **Clear status indicators**: Visual prominence for task notifications so drivers see them
5. **Fast load times**: Next.js SSR and Tailwind CSS minimise JavaScript payload

---

## Future Review

Revisit this decision if:
- Driver retention is low and user research identifies native app as a key request
- Push notifications become critical to operational efficiency
- Platform validates unit economics and investment in native app is justified
- Team grows to include mobile developers

**Target trigger**: After 6 months of operation with 500+ active drivers, conduct user research to determine if native app investment is warranted.

**Likely path**: React Native app for drivers only (highest mobile usage), keeping web for merchants and admin.

---

## Alternatives Considered

### React Native (iOS + Android)
Deferred. Most appropriate native option due to code sharing potential with existing TypeScript codebase. Revisit at Month 6+ when scale and user feedback justify the investment.

### Flutter
Rejected. Different language (Dart) from existing tech stack. No code sharing with Next.js frontend.

### Ionic (hybrid webview)
Considered but rejected. Adds app store complexity without meaningfully better performance than a well-optimised PWA. The middle ground between web and native without the best of either.

### Native iOS/Android (Swift/Kotlin)
Rejected. Completely separate tech stack, requires platform-specific developers. Not appropriate for a solo developer.
